# 设计取舍记录

> 面试官最容易问"为什么这么做"。这里把每个决策的**备选方案**和**放弃理由**都写清楚，比 README 更适合在面试前半小时过一遍。

## 1. 为什么规则算分、模型说话，而不是让模型直接判断商机

- 备选：把客户数据全丢给模型，让它输出"该不该增投"。
- 放弃理由：① 不可审计——销售问"为什么说这个客户要流失"，模型答不出规则；② 不稳定——同样数据两次跑出两个结论，业务方无法建立信任；③ 成本高——几百个客户批量扫一遍要几百次调用。
- 现在的做法：`scoring.py` 里五条流失信号、六类商机规则，阈值统一放在 `config/rules.json`——改口径不用改代码、不用重新发版，填错了（比如把 0.2 写成 20）会被校验拦下并回落默认值，不会让服务起不来。模型只在"把事实组织成人话"这一步出现。模型失败时规则模板兜底，功能不降级。

## 2. 为什么用 BM25 而不是向量检索

- 备选：Chroma / FAISS + bge-m3。
- 放弃理由：① 作品集要保证 clone 即可跑，Windows + Python 3.13 上装向量库容易翻车；② 语料只有几千字，BM25 召回够用；③ 可解释——能展示"哪几个词命中了这段"，评估时好归因。
- 代价与后续：同义改写召回弱（例如客户说"跑不动"而文档写"投不出去"）。接口已按 `retrieve(query, top_k)` 收敛，换实现只改 `tools/rag.py` 一个文件。中文没有引入 jieba，用"单字 + 二元组"，避免分词错误导致漏召回。

## 3. 为什么路由是"规则优先"，而不是全交给模型分类

- 备选：每次提问都先调一次模型做意图分类。
- 放弃理由：① 延迟与成本翻倍；② 分类错误时会静默走错分支，比"没命中"更难排查。
- 现在的做法：关键词规则先判，命中即走；只有全不命中才调模型。代价是关键词表需要维护，评估里 H01/H02 两条失败就是规则覆盖不到的边界——这也是我把它写进"已知短板"而不是藏起来的原因。

## 4. 为什么 Text-to-SQL 要三层防护

- 风险：模型生成的 SQL 可能写 `DELETE`、访问系统表、或者拼多条语句。
- 三层：① `guard()` 正则白名单——只允许单条 SELECT、表名白名单、禁止 DDL/DML/PRAGMA/ATTACH；② 只读连接（`file:...?mode=ro`），即使 guard 漏判也写不进去；③ 模板兜底——常见统计问题不依赖模型也能出数。
- 另外限制了返回行数（50 行），避免一次查询把结果集打爆前端。

## 5. 为什么要一个 review 节点

- 备选：让模型自己在提示词里"注意引用、注意数字"。
- 放弃理由：提示词约束无法度量，也无法在失败时兜底。
- 现在的做法：review 用代码检查三件事——有没有数字、引用是否在正文出现、长度是否够。不通过回退重跑一次；离线模板重跑不会变好，所以第二次直接在回答末尾追加"自检提示"，把不确定性暴露给使用者。评估里"自检通过率"这个指标就是给这个节点的价值做的度量。

## 6. 为什么状态里不放对话原文

- hello-agents 第 9 章讲上下文工程时提到，状态越滚越大是 Agent 长会话的主要失败原因。
- 现在 `AgentState` 只装结构化事实（意图、客户 ID、证据、轨迹），对话历史交给 checkpointer；每轮开始时显式重置 `trace`、`advertiser_id`，避免上一轮的客户被带进这一轮。这个坑我在批量问答时真踩过：`advertiser_id` 没清空，导致"今天该跟进谁"被当成单客户问题，图上还打转。

## 7. 为什么数据要自己造且表间强一致

- 演示最怕"数字对不上"：计划消耗之和 ≠ 客户消耗、月度指标最后一月 ≠ 30 天消耗，面试官一眼就看穿。
- `generate_data.py` 里显式约束：计划消耗按权重拆等于客户 30 天消耗；月度指标最后一个月直接对齐；CVR/CPC/ROAS 由点击与转化反算。固定 seed，任何人跑出来完全一致。
- 同时刻意埋信号：消耗下滑、CVR 走低、到期临近、断档超 21 天——没有这些信号，规则引擎和评估都无从验证。

## 8. 为什么比较类问题要"先判意图、再定指标"

- 问题："A003 比上个月好还是差"里没有"下滑"这类分析词，只有"好还是差"，按原来的词表会被商机分支截走，答成一堆建议。
- 做法：路由里加一个 `is_compare()`，只认两种**算得出对比**的问法——环比（比上个月/走势）和双客户对比（A003 和 A011）；命中就先走分析，再由 `pick_metric()` 决定比的是消耗、CVR、ROAS 还是转化成本。
- 为什么不把"对比""谁更"这类词全放进去：那会把"A011 对比同行怎么样"也拉进分析分支，而模板根本没有同行数据，最后只能答"暂时没法转成查询"——宁可让它走商机，也不要给一个假的分析。
- 结论层配套改了两处：跨客户要说清"谁高/谁低、高多少"，月度环比要逐指标给变化率并判断"整体变好/变差/有好有差"。只报一个总消耗的变化率，是销售最不买账的那种回答。

## 9. 为什么 SQLite 改成"每线程独立只读连接"

- 备选 A：全局共用一个可写连接（原实现）。放弃理由：FastAPI 的同步处理函数跑在线程池里，`sqlite3` 连接不是线程安全的，16 并发 × 200 请求实测 **44 次 `InterfaceError` / 22% 失败**。
- 备选 B：共用连接 + 全局锁。放弃理由：错误确实归零，但所有查询被串行化，并发总耗时从 2.18s 涨到 6.26s，属于"用吞吐换正确性"，不划算。
- 现在的做法：`threading.local()` 每线程一个 `mode=ro` 连接。只读连接天然线程安全、可并行读，还顺手堵死业务查询误写库；`close()` 统一关闭所有已建连接。16 并发失败数 0，并发 p50 从 101.66 ms 降到 46.26 ms。

## 10. 为什么要给会话状态设上界，以及生产为什么要能关掉 checkpointer

- 风险：`MemorySaver` 会为每个新 `thread_id` 永久保存 checkpoint / writes / blobs，公网访客每人一个会话，不淘汰就是线性内存泄漏。实测 **+500 会话 ≈ +12.25 MB**，且每请求都在写入状态。
- 备选：直接删掉 checkpointer。放弃理由（作为默认值）：作品集要保留"多轮状态 + 状态瘦身"这一设计点，`docs` 和 README 都写过，不该为了跑分悄悄改掉。
- 现在的做法分两层：① 默认保留 `MemorySaver`，用 `MAX_SESSIONS`（默认 256）做**滞回 + 批量 FIFO 淘汰**——超过上限 10% 才触发，一次清到 80%，避免每请求全表扫描 writes/blobs；② 增加 `USE_CHECKPOINTER=false` 开关，生产部署编译无 checkpointer 的图，彻底消除会话状态。
- 代价与数据：关掉后多轮状态不可用，但本项目每轮 `init` 本来就会显式重置 `advertiser_id` 与 `trace`，单轮问答不受影响——37 条答案与优化前**逐字节一致**。生产模式 +500 会话内存 +0.03 MB，单请求 p50 3.25 ms、并发 p50 28.28 ms。
- 淘汰是"尽力而为"：并发清理可能撞上正在写入的 checkpoint，所以整段包在 `try/except` 里，失败只记 debug 日志，绝不影响本次回答。

## 11. 为什么模型调用要加熔断，而不是只靠"失败降级"

- 原实现：`timeout=30` + `max_retries=2`，最坏一次问答要等 90 秒；且每次请求都重新尝试，模型不可用时整个 uvicorn 线程池会被慢请求占满。
- 现在的做法：超时 8s、重试 1 次；连续失败 3 次开启熔断，冷却 30s 内 `available=False`，router 和各节点直接走规则模板，一次网络调用都不发；冷却结束自动半开重试。
- 可观测性：`/api/health` 暴露调用数 / 失败数 / 降级数 / 平均耗时 / 熔断状态，日志只记异常类型，不打印 Key 或完整响应。
- 伦理与透明性不变：数值仍全部由规则引擎计算，模型只负责表达；回答仍带引用与执行轨迹；数据仍是模拟数据。熔断只改变"这一句话由谁写"，不改变任何数字口径。

## 12. 为什么记忆层要和 checkpointer 分开做

第 10 节为了并发正确性，给了生产模式一个开关：关掉 checkpointer。但那是"图的执行状态"（每个节点跑完往里写快照），如果多轮上下文也指望它，关掉的同时记忆就没了——性能和功能被迫二选一，这不合理。

所以把两类状态分开：
- **checkpointer** 服务图内部（重试回到哪个节点、节点间传什么），是执行细节，生产可关；
- **ConversationMemory** 服务用户可见的对话（问了什么、答了什么、意图、客户），是产品能力，始终在。

记忆只存回答摘要（前 240 字）而不是全文，因为它只用来做两件事：路由判断指代、给在线模型一点背景。全文既撑大上下文又容易让模型复述旧数字——而数字的唯一真相是本轮工具的返回结果。

## 13. 为什么指代消解是规则，不是模型

"他/继续/还有呢"这类追问，规则匹配足够了，而且零延迟、离线可用、可单测。更重要的是它可解释：trace 里明确记了"客户沿用上一轮 A003""追问沿用上一轮意图"，销售能看清系统凭什么知道在说谁。让模型猜指代，既慢又会在批量问题（"其他客户呢"）上误绑定到单个客户。

一个必须处理的反例：分析类追问（"还有呢"）本身没有查询词，继承了 analysis 意图后，如果只把这两个字交给 Text-to-SQL，转不出 SQL、反而回一句"暂时没法转成查询"——有了记忆比没记忆更差。所以 `_sql_question()` 会把上一轮的分析问题补全进本轮查询，让"还有呢"真的能出数。

## 14. 持久化为什么整会话重写，不做增量删除

最初按 `seq` 增量删旧轮次，测试立刻抓到：重启后 4 轮变 3 轮。原因是轮次裁剪会让前半段被切掉，剩余轮的 `seq` 前移，按旧 `seq` 删除就会漏删或错删。会话轮数本来就有上限（默认 12），改成"删掉该会话所有行、再全量写回"又短又不会错——用一点写入量换状态一致，在这scale 下是划算的。测试里专门有一条 `test_persistence_survives_restart` 盯着这个回归。

## 15. 为什么评估要拆成验证器/归因/回归三块（而不是只看四个百分率）

四个百分率（意图/事实/引用/自检）能回答"做对了多少"，回答不了"为什么错、错在哪一步、改了以后会不会又坏"。第 7 章给了三件不同的工具，各解决一个问题：

- **验证器**解决"通过是真的吗"。旧的关键词命中会把"不支持近45天，但合计 1,464,090"判成通过（因为出现了"45"）——ReAct 式自我陈述不可信，验证器必须核对可复核的客观事实。所以 refusal 类验证器带 `forbid_substrings` 一票否决：说了拒绝又漏出编造数字，照样失败。
- **失败归因**解决"错在哪一步"。把最后的报错当根因是最常见的误判。归因器按错误签名扫轨迹，定位**首个**偏离步，并区分根因（模糊命中模板）与后果（后续模板汇总）。责任方记为 `harness/tool` 而非"模型能力差"——因为这是口径拦截缺失，换模型也修不好。
- **轨迹前缀回归**解决"改了会不会又坏"。冻结上下文前缀，只验证下一步决策落在可接受动作集合内。H07 修复后，除了把它升级成 refusal 用例，还加了 PFX-04「追问继承到 A003 后，近45天仍要拒绝」——专门防止记忆层把护栏绕过去。

三块对应 SWE-bench 的 FAIL_TO_PASS（验证器+归因证明问题真修好了）与 PASS_TO_PASS（保留集+前缀回归证明没引入新缺陷）。

## 16. 边界集 + 保留集：为什么改动要在两套用例上验证

只测"应当被修复"的边界用例，会把过拟合当成进步（针对 H07 写死一个判断，别的自定义窗口又错了）；只测"不该受影响"的保留用例，会把无效修改当成安全（什么都没改，保留集当然全过）。所以 cases.jsonl 每条标 `set`：boundary（H07/A07）与 retention（其余 35 条）。

回归时的硬约束：**边界集 2/2 通过 + 保留集 35/35 逐字节一致 + 前缀回归 4/4**。37 条答案快照比对确认改造前后只有 H07 变化——这是"最小 diff + 可回滚"在评估层的落实。A07「全库消耗合计多少」特意和 H07 一起放进边界集：它问的正是近 30 天全库汇总（合法），放进边界集是为了盯住拦截规则别把它误伤了。

## 17. 为什么动作分类只看 evidence，不扫答案文本

轨迹前缀回归要把执行结果归类成"可观察动作"。第一版分类器先扫答案文本里的拒绝信号词（"不支持/口径/没法"），结果 PFX-03 的合法月度查询因为结论里出现"主要矛盾看口径ROAS"被误判成拒绝；PFX-02 的全库汇总因为 SQL 是 `SUM(spend_30d)` 无 WHERE 被误判成错误动作 `return_total_spend`。

改成**先看 evidence 的客观事实**：是否触发 `unsupported_window` 护栏、执行的是什么 SQL（含 `metrics` 就是月度查询），没有 SQL 才回退到答案文本。这正是提议者—审核者原则——审核方看的是产物与客观证据，不是产出方的自述。同时给前缀用例加 `forbid_substrings`：动作类别即使"看起来合法"，答案里出现被禁止的编造数字也一票否决。

## 18. 为什么工具要做成"注册中心"而不是散落在节点里

旧版节点直接调 `store.get_advertiser()` / `kb.retrieve()` / `sql_agent.nl_to_sql()`，新增一个外部能力要同时改 Context、节点和文档，失败处理各写一遍。现在所有能力先注册成 `ToolSpec`，调用方只认名字和参数 schema：

- **统一接入**：13 个内置工具在 `tools/bootstrap.py` 一处注册，新增工具加一条 spec 即可，规划器通过 `registry.describe()` 自动发现；
- **参数校验前置**：`advertiser_id` 这类来自 API 的输入用 `^A\d{3}$` 约束在入口挡住，不再依赖调用方自觉；
- **统一结果**：`ToolResult` 把成功数据、错误码、用户安全文案、内部 detail、耗时、降级标记、警告收在一个对象里，上层能按同一套规则汇总置信度；
- **可观测**：每个工具的调用/失败/降级/延迟进 `registry.metrics()`，能回答"是谁失败了、谁拖慢了回答"。

没有选完整 JSON Schema + 自动 function calling：依赖会变重，而且模型侧工具调用本身不稳定。轻量 dict schema 覆盖真正用得上的约束，离线规则也能解析。

## 19. 为什么超时用线程池但不强杀线程

`ToolRegistry.call()` 允许给工具设 `timeout_s`，底层用 `ThreadPoolExecutor + Future.result(timeout)`。超时后立刻返回 `tool_timeout` 并走回退，但工作线程不强制中断——Python 无法安全杀线程，强杀可能留下半写状态。对本地只读工具来说这是可接受的：超时本身是保险，不是常规路径。

SQLite 连接是线程本地的，线程池复用固定 worker，连接数上界等于 worker 数（8），不会随请求增长。

## 20. 为什么规划器只改变复合任务，不动单意图路径

规划层最大的风险是"聪明过头"：把原本稳定的 37 条用例答案改坏。因此加了硬边界：

- router 先按老规则判意图；Planner 只是在后面补一份计划；
- `graph._dispatch()` 只有看到 `plan.mode == "composite"` 且子任务 ≥ 2 才切到编排节点，其余情况走原来的原子节点；
- 复合判定要求连接词拆分后至少出现两个不同意图，追问语（"继续/还有呢"）不算新任务。

验证方式是拿 HEAD 的干净 worktree 导出基线，逐条比对 37 个问题的答案/意图/引用/自检字段——本轮改动后差异为 0。这是边界集/保留集方法论在工程改动上的延续：先证明没坏，再谈变好。

## 21. 为什么子任务失败要隔离，而不是整体报错

复合任务里一个子工具失败不应让整份回答消失。`orchestrate_node` 对每个子任务单独 try/except：失败项给出安全的错误文案并标记 `review.ok=False`，其他项照常产出；最后 `integrate()` 把失败信息放进 `warnings`、把置信度打折，而不是伪造数据补齐。这样用户至少拿到部分可用信息，同时明确知道哪一块不可信。

数字核对（`number_mismatch`）也遵循同一原则：只在 `warnings` 里提示可疑数字，绝不改写正文——正文里的数字来自规则与只读 SQL，模型润色不得覆盖事实。

## 22. 为什么错误码要分成 message / detail 两层

早期 SQL 执行失败会把异常原文直接回显给用户，里面可能带数据库路径和内部列名。现在统一用 `AgentError`：`message` 是固定安全文案，`detail` 只进日志和 `evidence.error`。`retryable` 字段区分"网络抖动可重试"与"参数错误别重试"，避免对配置问题重复发起调用。前端可以按 `code` 做差异化展示，但拿不到内部细节。

## 23. 为什么定时任务默认不改代码，只做验证与同步

"自动优化"最容易失控的地方是让无人值守的任务直接改写源码：没有评审、没有上下文、失败时还留下半成品。这里把边界划在流程上：任务只做**验证、评估、提交已有改动、同步两端**，代码优化仍由开发者在会话中完成并由任务做质量把关。这样每晚得到的是"当前状态是否健康、改动是否已同步"的确定性结论，而不是不可预测的代码差异。

## 24. 为什么用三重去重而不是只看日期

只按日期去重会漏掉两类真实场景：上次推送失败后次日需要补推、以及手动强制重跑。因此同时做了文件锁（防并发）、当日状态（防重复跑）、内容检查（防重复提交/推送）。`--force` 只绕过第二层，另外两层仍然生效——这正是"可手动触发但不会造成重复更新"的关键。

## 25. 为什么评估不达标时必须阻断推送

评估通过率是推送的前置门禁。若验证或评估失败后仍允许提交推送，会把坏状态同步到两端，凌晨无人值守时难以察觉。默认 `continue_on_failure=false`，失败即中止且状态文件不记成功；次日仍可重试，不会把失败"记成已处理"。
